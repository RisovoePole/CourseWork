# CP-SAT — `scheduling_cp_sat.py` (OR-Tools)

## Как работает именно эта реализация

1. **Hard-constraint'ы не штрафуются — они физически не представимы.** В отличие от TS/GA/SA, где `hard_professor_qualified`/`hard_room_capacity`/`hard_room_type` — это функции, считающие нарушения постфактум, здесь H2 (квалификация) и H3+H4 (вместимость+тип аудитории) — это **ограничение домена**: переменная `professor_idx`/`audience_idx` для сессии может принимать только индексы из уже отфильтрованного `SessionCandidates`. Недопустимое значение просто не существует как вариант.
2. H1 (уникальность слота) — кодирую `slot_id = weekday * P + timeslot` и требую `add_all_different` по всем `slot_id`. Это превращает пару (день, пара) в одно число ровно для удобства `AllDifferent`.
3. **H5 (дневной лимит) оказался следствием H1, а не отдельным правилом.** Раз `AllDifferent` запрещает повтор `slot_id`, а `timeslot` и так ограничен `P` значениями — на один день физически не может прийтись больше `P` сессий. Добавляю `count_d <= pairs_per_day` явно всё равно — это избыточный, но дешёвый и наглядный дубль.
4. День-индикаторы `day_bool[i][d]` строю через двустороннюю реификацию (`weekday == d` влечёт `b`, `weekday != d` влечёт `not b`) — это даёт настоящий `iff`, а не одностороннюю импликацию. Из этого же автоматически следует "ровно один день на сессию" — отдельный `add_exactly_one` не нужен.
5. Компактность дня (`gap_d`) считаю через `min_slot_d`/`max_slot_d`, привязанные к `day_bool` через `only_enforce_if`. Для пустого дня (`used_d == False`) `gap_d` принудительно зануляется отдельной веткой — без этого решатель мог бы "обнулить" разрыв на пустом дне произвольно (или даже получить отрицательный gap), потому что без ограничений `min_slot_d`/`max_slot_d` ничем не закреплены.
6. Равномерность по неделе считаю не дисперсией, а **range** (`max(пар/день) − min(пар/день)`) — потому что objective у CP-SAT обязан быть линейным, а дисперсия — это сумма квадратов.
7. Один `model.minimize(...)` на все три soft-критерия сразу (взвешенная сумма), hard в этой сумме вообще не участвует — ему просто негде нарушиться.
8. После `solver.solve()` декодирую `Vec` из индексов и прогоняю результат через `evaluate()` из TS-модуля — не как часть решения, а как **сверку**: `hard` обязан получиться 0, иначе это баг в переводе constraint'ов в модель, а не особенность данных.

## Что крутить и как понять, что крутить

| Параметр | Эффект | Когда трогать |
|---|---|---|
| `max_time_in_seconds` (30.0) | бюджет на доказательство оптимальности | смотреть `result.status_name`: `OPTIMAL` — уже всё, нечего крутить; `FEASIBLE` — решение валидно, но не доказано как лучшее, можно дать больше времени; `UNKNOWN` — даже допустимого решения не нашли за бюджет |
| `seed` (`random_seed`) | тай-брейк при ветвлении поиска | не влияет на корректность, только на то, какое из равно-хороших решений найдётся первым/быстрее |
| `W_COMPACT`/`W_ROOMFIT`/`W_BALANCE` (модульные константы) | вес каждого soft-критерия | то же замечание, что в TS/GA/SA — поменять баланс между критериями можно только правкой исходника, в сигнатуру `solve_with_cp_sat()` не прокинуто |

Главное отличие от TS/GA/SA в диагностике: **есть явный статус**, а не только число. `INFEASIBLE` означает, что решения не существует вообще при текущих данных — это не лечится никаким тюнингом параметров, нужно смотреть данные (скорее всего сработает один из `ValueError` в `build_session_candidates` ещё до решателя — у какой-то дисциплины нет ни преподавателя, ни подходящей аудитории).

## Особенности реализации

- И преподаватель, и аудитория кодируются как **локальный индекс** в отфильтрованном списке кандидатов конкретной сессии (`professor_idx`, `audience_idx`), а не как реальный id напрямую. Для преподавателя это просто индекс без доп. constraint'ов (по построению он уже допустимый). Для аудитории нужен `add_element(audience_idx, [seats...], seats)`, потому что `seats` участвует в soft-objective (room-fit), а индекс сам по себе число вместимости не знает.
- В отличие от TS, где баг с алиасингом табу шёл от того, что несколько сессий одной дисциплины делят один `discipline_id`-ключ — здесь это не проблема: у каждой сессии **свой набор переменных** по позиции в списке, никакого общего ключа, по которому могло бы что-то слипнуться.
- `gap_d`, `count_d`, `day_bool` считаются один раз и используются и для (избыточного) H5, и для soft-критериев — не пересчитываются дважды.

## Чем плох / недоработки

- Веса soft-критериев — те же захардкоженные модульные константы, что и в TS/GA/SA, не параметризованы.
- `max_count - min_count` (range) — не то же самое, что `soft_week_balance` (дисперсия) у TS/GA/SA. Это значит, что компонента "равномерность" в итоговом `soft` не сравнивается 1-в-1 между CP-SAT и остальными тремя алгоритмами, даже после прогона через общий `evaluate()` — `evaluate()` всё равно считает дисперсию по готовому расписанию, так что итоговая сверка корректна, но сам процесс оптимизации внутри CP-SAT целится в другую метрику равномерности, чем то, что в итоге измеряется.
- Нет `add_hint(...)` — решатель стартует с нуля каждый раз, хотя для бенчмарка (много прогонов с похожими параметрами) можно было бы подсказывать предыдущее найденное решение.
- Количество потоков решателя не настроено явно (оставлено на дефолт "взять всё доступное") — параметр для ограничения существует, но я не стал жёстко фиксировать его имя в коде, потому что оно менялось между версиями OR-Tools.
- На `INFEASIBLE` нет диагностики "из-за чего" — CP-SAT умеет находить минимальный конфликтующий набор ограничений (через assumptions), здесь это не реализовано: просто получаешь `INFEASIBLE` без объяснений, если данные уже прошли проверки в `build_session_candidates`, но конфликт возник на уровне `AllDifferent` (например, сессий больше, чем доступных слотов).
- Soft-критерии собраны в одну взвешенную сумму, хотя у CP-SAT есть честный способ сделать **лексикографическую** оптимизацию (сначала минимизировать compactness, зафиксировать результат как constraint, затем минимизировать balance, и так далее) — если нужен жёсткий приоритет между soft-критериями, а не их взвешенная смесь, сейчас этого нет.

## Точки расширения

- Новый hard-constraint почти всегда — это правка `build_session_candidates` (сузить домен) или один `model.add(...)`, без переписывания остального.
- Новый soft-критерий — отдельное линейное выражение + слагаемое в `model.minimize(...)`; `day_bool`/`day_count` уже посчитаны и готовы к повторному использованию для любых дне-зависимых метрик.
- `SessionCandidates` — общая точка, где можно добавить любую дополнительную фильтрацию (например, "эта аудитория есть только по вторникам") без изменений в остальной модели.

## Что стоит добавить

- `model.add_hint(...)` с решением от TS/GA/SA как стартовая подсказка — на больших инстансах может сильно сократить время до `OPTIMAL`.
- Явная настройка числа потоков решателя (проверить актуальное имя параметра в установленной версии OR-Tools и зафиксировать).
- Диагностика причины `INFEASIBLE` через `add_assumptions`/`sufficient_assumptions_for_infeasibility` — сейчас даже не известно, какая именно дисциплина/группа стала проблемной.
- Лексикографическая многоступенчатая оптимизация soft-критериев вместо взвешенной суммы — если для курсовой важен строгий приоритет (например, "сначала минимум hard, потом обязательно минимум compactness, и только при равенстве — смотрим на balance"), а не их смесь.
- Привести `soft_week_balance` внутри CP-SAT к той же дисперсии, что в TS/GA/SA (через кусочно-линейную аппроксимацию квадрата) — если для курсовой принципиально важно, чтобы все четыре алгоритма оптимизировали ровно одну и ту же soft-метрику, а не просто сравнивались по её итоговому значению постфактум.
