# Tabu Search — `scheduling_tabu_search.py`

## Как работает именно эта реализация

1. `build_initial_schedule` строит старт: сессии раскладываются по перемешанному списку всех слотов `(weekday, timeslot)` циклически (`i % len(all_slots)`). Если сессий больше, чем слотов — слоты переиспользуются с первой итерации, то есть **старт гарантированно может быть инфизибл по `hard_unique_slot`**. Аудитория и преподаватель на старте выбираются случайно, но **уже с фильтром** по `professor_discipline` и `optimal_room_type` — это единственные hard-constraint'ы, которые учтены при конструировании, остальные (`hard_room_capacity`, `hard_daily_limit`, `hard_unique_slot`) отдаются на исправление самому TS.
2. На каждой итерации генерируется **батч** случайных ходов (`neighborhood_size`, по умолчанию 25), а не один ход. Из батча выбирается лучший допустимый (не табу или прошедший aspiration), даже если он хуже текущего решения — стандартный механизм TS для выхода из локального оптимума.
3. Табу — **атрибутный**, не по полным решениям: в лист пишется `(discipline_id, "slot"/"audience"/"professor", старое_значение)`. Это намеренно отличается от `continuos_radius`-зон из `edgarsmdn/TS` — там это вообще не имело смысла для дискретной задачи.
4. Критерий устремления (aspiration) — один: ход разрешён вопреки табу, если итоговый `(hard, soft)` лексикографически лучше лучшего найденного.
5. Если весь батч оказался под табу — берётся случайный ход **без проверки и без оценки** (чистая диверсификация, не градиентный выбор).
6. Останов: либо `max_iterations`, либо `hard == 0` и `stagnant_for >= stagnation_limit` подряд без улучшения.

## Что крутить и как понять, что крутить

| Параметр | Эффект | Когда трогать |
|---|---|---|
| `neighborhood_size` (25) | больше = лучше ход за итерацию, но `evaluate()` вызывается `neighborhood_size` раз за итерацию — линейный рост стоимости | если за разумное число итераций `hard` не идёт к 0 — увеличить, чтобы чаще натыкаться на удачные ходы |
| `tabu_tenure` (20) | длина памяти запретов | зацикливание/частый возврат к тем же состояниям → увеличить; застой (soft не падает) при `hard == 0` → тоже увеличить, чтобы не возвращаться в ту же яму |
| `max_iterations` / `stagnation_limit` | критерии останова | смотреть `history`: если `soft` давно не падает, а `hard` уже 0 — можно сокращать `stagnation_limit` |
| `W_COMPACT` / `W_ROOMFIT` / `W_BALANCE` (модульные константы, **не параметры функции**) | вес каждого soft-критерия в сумме | хочешь другой баланс между компактностью/вместимостью/равномерностью — **редактировать исходник**, через сигнатуру `tabu_search()` это не прокинуто |

Диагностика: `result.best_objective = (hard, soft)`. Если `hard > 0` после прогона — это либо нехватка итераций/`neighborhood_size`, либо структурная инфизибильность данных (нет преподавателя на дисциплину, нет подходящего типа аудитории) — никакими гиперпараметрами это не лечится, нужно проверять исходные данные.

## Особенности реализации

- `evaluate()` пересчитывает hard/soft **с нуля по всему расписанию** на каждый кандидат — инкрементальной (delta) оценки нет. При `neighborhood_size=25` это 25 полных проходов по списку сессий на одну итерацию TS.
- `apply_move` каждый раз делает `schedule.copy()` — то есть на каждый кандидат батча создаётся полная копия `Schedule`, даже для отклонённых вариантов.
- `swap_slots` меняет местами только `(weekday, timeslot)`, аудиторию и преподавателя не трогает — это единственный ход, который физически не может сломать `hard_professor_qualified`/`hard_room_type` (они привязаны к самой Vec, а не к слоту).

## Чем плох / недоработки

- **Баг с алиасингом табу-атрибутов.** `SessionSpec` не хранит уникальный id сессии — у дисциплины с несколькими парами в неделю (например, 2 лекции) все её `Vec` имеют одинаковый `discipline_id`. Табу-атрибут `(discipline_id, "slot", старый_слот)` после этого может запретить откат **не той самой** сессии, а любой другой сессии той же дисциплины, которая туда даже не ходила. Лечится добавлением уникального `session_id` в `SessionSpec`/`Vec` и переходом на индекс вместо `discipline_id` в атрибуте.
- Конструктор старта не проверяет вместимость и дневной лимит вообще — это целиком работа TS, что увеличивает число итераций до первого `hard == 0`.
- Нет инкрементальной оценки — стоимость итерации растёт линейно с `neighborhood_size × len(sessions)`.
- Единственный механизм диверсификации — случайный ход без оценки, когда весь батч табу. Нет рестарта/повторного разогрева, если застряли надолго при `hard == 0`.
- Soft-веса — захардкоженные константы модуля, а не параметры `tabu_search()`.

## Точки расширения

- Новый вид хода — добавить ветку в `generate_candidate_moves` и `apply_move`, ничего другого менять не нужно.
- Новый hard/soft-constraint — отдельная функция + одна строка в `evaluate()`.
- Гранулярность табу-атрибута легко меняется (см. баг выше) — параметр того, что именно класть в `tabu_attrs`.

## Что стоит добавить

- Уникальный `session_id` — закрывает баг с алиасингом и одновременно открывает дорогу к kind-специфичным правилам (например, room-type только для `"lab"`).
- Инкрементальная оценка `Δhard/Δsoft` от одного хода вместо полного `evaluate()` — самое дешёвое и самое заметное ускорение.
- Параметризация soft-весов через сигнатуру `tabu_search(...)` вместо модульных констант.
- Механизм рестарта/повторного разогрева при долгом застое на `hard == 0` (сейчас просто останавливается).
